正規化すべき
タイミング

「なんとなく感じる気持ち悪さ」を
第1〜第3正規化の言葉で説明できるようにする。

第1正規化：1つのセルに1つの値

NG — カンマ区切りで保存
tags = "Ruby,Rails,SQL"
OK — 別テーブルに分離
tags テーブル + 中間テーブル
NG — JSON 配列
colors = ["red","blue"]
OK（検索しないなら JSON 許容）
別テーブルに1行ずつ
NG — 連番カラム
phone1, phone2, phone3
OK
phones テーブルに
user_id + number で複数行

第2正規化：重複を除去

NG — 毎行に顧客情報を重複保存
orders テーブルに
customer_name
customer_address
を毎回保存している
OK — テーブルを分離して参照
customers テーブルに切り出して
orders.customer_id で参照
→ 変更は 1箇所だけで済む
判断基準
「〇〇を変えたら全部の行を更新しないといけない」
→ 正規化できていない証拠。別テーブルに切り出す。

第3正規化：推移的従属の除去

NG
products に category_id と category_name を両方持つ
OK
categories テーブルに name を持たせ
category_id だけ参照

逆に非正規化してよいとき

集計・サマリーが毎回遅い
→
counter_cachesummary テーブルに定期保存
JOIN が多すぎて複雑になった
→
denormalize して同テーブルに「更新は1箇所だけ」を担保
読み取り専用のレポート用
→
マテリアライズドビュー
以前の状態を記録として残す
→
スナップショットとして直接保存マスタ変更の影響を受けない

勘どころ
まとめ

設計を始める前と、詰まったときに
手を止めて確認するチェックポイント。

設計前に必ず答える 5 問

Q1
この値が変わったとき、何行の更新が必要か？
複数行 → 正規化すべき　　1行 → OK
Q2
このカラム、NULL になるレコードはあるか？
多い → 別テーブルへの切り出しを検討
Q3
このデータ、他のテーブルにも同じものがあるか？
ある → 外部キーで参照する設計に変える
Q4
集計・検索・並び替えをするか？
する → 正規化してカラムに持つ　　しない → JSON でも許容
Q5
将来この項目が増える可能性があるか？
ある → 別テーブルに切り出す　　ない → カラムで十分

多対多を見抜くパターン

「ユーザーは複数のグループに入れる」かつ「グループには複数のユーザーがいる」
→ 多対多 → 中間テーブル確定

マイグレーション戦略

図解
「一気に移行する」は避ける
→
加算 → 確認 → 削除 の3ステップ
バックフィルは冪等にする
→
find_or_create_by何度実行しても同じ結果に

セッション vs URL スコープ

NG — セッションでグループを持つ
session[:current_group_id]

タブ複数開くと混乱する
セッション切れで権限が崩れる
URL をブックマークできない
デバッグしにくい
OK — URL でスコープする（推奨）
/groups/:group_id/dashboard

タブごとに独立して動作
URL をブックマーク可能
before_action で確認するだけ
デバッグしやすい
